# Browser hostname convention

Every browser-facing app must use `<instance>.localhost:<published-port>`, including host-run/non-Nuxt apps. Do not report bare `localhost` or `127.0.0.1` as the app URL. Run `stackfork where` before adapting the app to obtain the deterministic hostname: the checkout name plus its path/branch hash. For a shorter project/issue name, select `prepare --hostname web-274.localhost` (or `api-571.localhost`) once; it is remembered. Explicit names must be unique across concurrent instances; default names already incorporate checkout/branch identity.

`prepare` supplies `DEV_HOSTNAME` for Compose interpolation; the Nuxt template also exposes it in the app environment. This variable is a hostname, not a URL or server bind address. Keep servers bound to `0.0.0.0` and container-to-container URLs on service DNS. Adapt the project's actual browser API origin, CORS/allowed hosts, auth callbacks and HMR settings to this hostname and the published ports. For host-run apps, use the same hostname returned by `where` and their actual listening ports. Do not assume setting `DEV_HOSTNAME` automatically configures a framework. Keep cookies host-only, never scoped to `.localhost`.

After startup, obtain endpoints from `stackfork urls` and verify login/HMR using the named URL in a browser. `urls` infers the HTTP scheme from a fixed list of common target ports; a custom port or protocol still needs project-specific interpretation, and it never prints credentials. Do not silently fall back to a bare loopback URL if DNS, host validation or callbacks fail; fix the adapter or report the blocker. Existing adapters need these settings checked before adopting the named URL — changing the helper's output alone does not migrate application configuration. Do not restart another agent's active stack just to adopt this convention.
