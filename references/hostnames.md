# Browser hostname convention

Every browser-facing app must use `<instance>.localhost:<published-port>`, including host-run/non-Nuxt apps. Do not report bare `localhost` or `127.0.0.1` as the app URL. Run `stackfork where` before adapting the app to obtain the hostname: by default the app (main checkout) name plus the worktree name, such as `acme-web-feature-invoices.localhost`, set by the `hostname` key of config.json (`references/commands.md`); an instance prepared before keeps its older `<checkout>-<hash>` name. For a shorter project/issue name, select `prepare --hostname web-274.localhost` (or `api-571.localhost`) once; it is remembered. Explicit names must be unique across concurrent instances; default names are made unique by `prepare`.

`prepare` supplies `DEV_HOSTNAME` for Compose interpolation; the Nuxt template also exposes it in the app environment. This variable is a hostname, not a URL or server bind address. Keep servers bound to `0.0.0.0` and container-to-container URLs on service DNS. Adapt the project's actual browser API origin, CORS/allowed hosts, auth callbacks and HMR settings to this hostname and the published ports. For host-run apps, use the same hostname returned by `where` and their actual listening ports. Do not assume setting `DEV_HOSTNAME` automatically configures a framework. Keep cookies host-only, never scoped to `.localhost`.

After startup, obtain endpoints from `stackfork urls`. It prints the recorded app entry first (`App: ...`), then the named links, then the service endpoints. Record the entry and links with `learn record entry` and `learn record link` (`references/learning.md`); until then the entry is a guess and `urls` marks it `guessed`. `stackfork open [NAME]` opens one in the browser. Verify login/HMR using the named URL in a browser. `urls` infers the HTTP scheme from a fixed list of common target ports; a custom port or protocol still needs project-specific interpretation, and it never prints credentials. Do not silently fall back to a bare loopback URL if DNS, host validation or callbacks fail; fix the adapter or report the blocker. Existing adapters need these settings checked before adopting the named URL — changing the helper's output alone does not migrate application configuration. Do not restart another agent's active stack just to adopt this convention.

## OAuth callback setup

An OAuth/OIDC provider's redirect URI must be registered against the exact origin `urls` prints, and only ever needs registering once per instance:

- **With stable ports (no proxy running), or the proxy not in use at all:** register `http://<hostname>:<port>` — the exact line `urls` prints for the service handling the callback. This is stable across `down`/`up`, container recreation and re-`prepare`: the host port doesn't move unless the user explicitly runs `prepare --reassign-ports`, so the redirect URI never needs updating again for that instance.
- **With the shared proxy running and routing this instance (`stackfork proxy up`):** register `http://<hostname>` with no port instead — `urls` switches to printing that form once the proxy is actually serving the instance. This is the more convenient one to hand to a provider that doesn't like a port number in its callback URL allowlist.

Either way, register once and leave it: don't re-register on every `up`, and don't ask the user to update the provider unless `urls` actually prints a different origin than before (a `--reassign-ports` re-prepare, or a proxy started/stopped for the first time). If the app config can only hold one redirect URI, prefer the proxy's portless form once the proxy is a normal part of the workflow; otherwise the stable-port form is just as durable.
